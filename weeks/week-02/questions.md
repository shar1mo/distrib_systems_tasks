# Вопросы для самопроверки

1. Чем `PUT` принципиально отличается от `PATCH`? Какой из них является идемпотентным?

- PUT полностью заменяет существующий ресурс. Если поле не указано в запросе, оно может быть сброшено в значение по умолчанию.
PATCH меняет только те поля, которые передал клиент, оставляя остальные без изменений.
Идемпотентным является PUT: если выполнить один и тот же PUT несколько раз, результат не изменится.
PATCH обычно не идемпотентен, потому что повторное применение может менять ресурс каждый раз.

2. Какие HTTP коды ошибок вы знаете и в каких ситуациях их следует возвращать?
   - 400 vs 422
   - 401 vs 403
   - 404

- 400 Bad Request — клиент прислал неправильный запрос по логике (например, неправильный JSON или отсутствуют обязательные поля).

- 422 Unprocessable Entity — данные валидны с точки зрения синтаксиса, но не проходят валидацию (например, число вместо строки или email невалидного формата).

- 401 Unauthorized — клиент не аутентифицирован, нужно войти в систему.

- 403 Forbidden — клиент аутентифицирован, но ему запрещено выполнять это действие.

- 404 Not Found — запрашиваемый ресурс не найден на сервере.

- 500 Internal Server Error — ошибка на стороне сервера, которую клиент исправить не может.

- Разница 400 vs 422: 400 — синтаксическая или логическая ошибка запроса, 422 — данные формально правильные, но нарушают правила валидации.
Разница 401 vs 403: 401 — нет токена или неправильный, 403 — токен есть, но доступа нет.


3. Зачем нужны негативные тесты (тесты на ошибки)?

- Негативные тесты проверяют, что сервер правильно обрабатывает некорректные запросы.
Они показывают, что сервис не падает, возвращает правильный код ошибки и понятное сообщение.
Это важно для стабильности, безопасности и корректной работы клиента.

4. Почему важно возвращать ошибки в структурированном формате (например, JSON), а не просто текстом?

- Структурированный формат позволяет клиенту автоматически парсить ответ, получать код ошибки, сообщение и дополнительные данные.
Если вернуть просто текст, клиенту придётся разбирать строку вручную, что ненадёжно и неудобно для фронтенда или мобильного приложения.

5. Что такое "обратная совместимость" API и как валидация помогает (или мешает) её поддерживать?

- Обратная совместимость — это когда старые клиенты продолжают работать после обновления API.
Валидация помогает, потому что она не пропускает некорректные данные, предотвращая падение сервиса.
Но слишком строгая валидация может мешать: если добавить новые обязательные поля, старые клиенты начнут получать ошибки.
Поэтому важно продумывать, какие поля обязательные, а какие — опциональные, чтобы новые версии API не ломали старые клиенты.
